Smart Housing Scout
Rent with evidence, not claims.
Assignment 9: Software Project

A web app for students who rent in Pittsburgh without seeing the home first. It ranks homes by real door-to-campus commute time, true monthly cost, and verified bathroom count, instead of what the listing says.

Code: github.com/srishti6singh/smart-housing-scout

1. Functional decomposition

The digital experience: an international student choosing an apartment in Pittsburgh, near Carnegie Mellon, before arriving in the city.

User objective

The users are college students from overseas who need to find accommodation before they arrive. They want to see what a place really looks like, and to know three things a listing may not tell them honestly: how long it really takes to get from the door to campus, not just how far it is (the Commute Truth-Teller); whether “2 baths” means two full bathrooms or one bathroom and a toilet-only washroom; and what the home will really cost each month with utilities. This matters because they need actual numbers to plan: a student with a $700 monthly budget and a $500 rent needs to know that utilities will stay under $200.

2A. Project description and architecture

Project description

Smart Housing Scout is a commute truth teller and lease time machine. It lets you know exactly what your house is like from overseas and if it truly fits your budget. It shows your true daily commute to campus, based on bus schedules, along with real stats and verified reviews from past renters.

Target user

The users are international college students moving to Pittsburgh who need to secure accommodation before they arrive.

Requirements

The app must rank homes by real door to campus commute time rather than distance. It needs to break the trip down into a visual Journey Bar, calculate the true monthly cost including utilities, flag mismatches in bathroom counts, let users compare options side by side, and work offline using sample data when no Google API key is set, and show a clear error message if the server is down.

How it works (logic and math)

If you select CMU, the app finds the actual bus going to CMU from a specific stop rather than a random one, aligning with transit APIs for accurate schedules (sample schedules until a Google API key is added). For the commute math, the total time equals your arrive by time minus your departure time, meaning early arrival is accurately counted as commute time. True cost is calculated by adding rent and estimated utilities based on square footage, season, and heating type. The Bathroom Detective compares the listed count against verified data where a half bath equals 0.5. It raises a red flag if the numbers do not match.

Success metrics

Success looks like students actually using the app to finalize houses without depending on Zillow, Google Maps, or video calling. Technically, success means all five test traps trigger correctly in the frontend development, commute segments perfectly add up to the total time, and the cost table perfectly matches manual calculations.

Testing plan

The testing plan relies on five built in traps to catch edge cases: a home that is physically close but has a slow commute, a farther home with a fast direct bus, a listing claiming 2 baths that is verified as 1.5, a cheap rent with hidden high utilities, and a home with great reviews but the longest commute.

2C. Code modification

The change

After using the app myself, I asked for four changes. The main one was the budget filter. Before, I could only pick a preset amount such as “Under $1,500”. Now I can type my own limit for rent and for utilities, and turn on “Match on total” (Figure 3).

The other three: the map can be resized by dragging the bar next to it, or hidden; every filter has its own Clear button, utilities has Select all, and there is a Clear all; and the Compare page can sort homes by shortest commute, lowest utilities, or lowest total cost.

Why

While browsing, I could not enter my own numbers. If my budget is $1,000 for rent and at most $250 for utilities, a house with $750 rent and $400 utilities should still show up, because the total fits. That is the same budget question as my user objective. The map always took about 30% of the right side of the home page, which did not make sense when I only wanted to look at the homes. And when comparing, I wanted to line homes up by commute or cost, the way you sort a list.

How

Claude wrote the code, and I tested it. The budget filter now stores three things: a rent limit, a utilities limit, and whether to match on the total. A small function, budgetMatch, checks a home: when both limits are set and “Match on total” is on, rent plus utilities must be within the two limits added together; otherwise each limit is checked on its own. Eight new unit tests check this, including my $750 + $400 example. In the browser, rent $1,200 and utilities $250 showed 3 homes with “Match on total” on and 2 with it off.

Testing the change also found a bug: the filter panel closed whenever the window resized. On a phone, tapping a number box opens the keyboard, which resizes the window, so the panel would close before you could type. It now moves into place instead of closing.

2D. Summary reflection

Systems approach. Before any code was written, I wrote one detailed prompt: who the users are, the three features, five test traps with the result I expected from each, the order to build in, an offline sample mode, and a rule that nothing counts as working until it has been run. Before building, I had the prompt reviewed, and the review found the biggest gap: “arrive by 8:45” hides the time lost by arriving early. That became a fifth part of the trip, and the total commute is now the arrive-by time minus the time you leave home. The five traps worked as my test plan, because each one has a result you can check.

Plan compared with the finished project. The main logic went as planned, but several things did not. My laptop did not have Node.js installed. The traps did not appear on their own; the sample bus schedules had to be adjusted until the closest home really was slow and the far one really was fastest. Google’s Routes API does not give a trip start time, so it had to be worked out from the trip length. And once I used the app myself, I asked for four changes that were not in my plan: typing my own budget, resizing the map, clearing filters, and sorting on the Compare page. The real Google transit data is still untested, because I do not have an API key yet.

Working with the AI. The AI was most helpful at turning a detailed prompt into a full working app quickly, with automated tests. It still needed checking. All 35 tests passed while the app showed a house with palm trees as a Pittsburgh listing, a confusing comparison between homes, and a phone layout where the search box was cut off; screenshots caught those. My own browsing found the changes that mattered most to a student, like typing my own budget. I stayed the director: I chose the features, the test traps, and the changes after testing.

Next time. I would write the exact expected number for each trap in the prompt, sketch the phone layout as well as the desktop one, get a Google API key early so real data can be tested, and try the app as a user sooner, because my own testing found the most useful improvements.

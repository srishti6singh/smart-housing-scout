Smart Housing Scout
Rent with evidence, not claims.
Assignment 9: Software Project

A web app for students who rent in Pittsburgh without seeing the home first. It ranks homes by real door-to-campus commute time, true monthly cost, and verified bathroom count, instead of what the listing says.

Question 1

Functional decomposition (3 points)

The digital experience: an international student choosing an apartment in Pittsburgh, near Carnegie Mellon, before arriving in the city.

User objective (1 point)

The users are college students from overseas who need to find accommodation before they arrive. They want to see what a place really looks like, and to know three things a listing may not tell them honestly: how long it really takes to get from the door to campus, not just how far it is (the Commute Truth-Teller); whether “2 baths” means two full bathrooms or one bathroom and a toilet-only washroom; and what the home will really cost each month with utilities. This matters because they need actual numbers to plan: a student with a $700 monthly budget and a $500 rent needs to know that utilities will stay under $200.

Logic

  • Departure: the Routes API gives no trip start time, so departure = final arrival − route duration.
  • Wait = bus departure − (departure + walk to stop). Transfer waits are added to the same bucket.
  • Early arrival = arrive-by time − actual arrival at the building.
  • Total commute = arrive-by time − departure. Early arrival counts, because the student spends it commuting.
  • True cost = rent + every utility not included in rent. Annual average = mean of 4 winter, 4 summer, and 4 other months.
  • Bath check: verified = full + 0.5 × half. Mismatch if it differs from the listed count.
  • Lease flexibility: +1 lease under 12 months, +1 early termination allowed, +1 sublease (+0.5 with approval), +1 notice of 30 days or less.

Question 2D

Summary reflection (3 points)

True events to draw from

Systems approach

  • The prompt defined the users, the five test traps, the data types, the build order, and an offline mode before any code was written. The traps worked as a test plan: each one has an expected result that can be checked.
  • A review of the prompt before building found the biggest gap: "arrive by 8:45" hides time lost to arriving early. That became the fifth segment and changed how total commute is defined.

Plan compared with the finished project

  • Node.js was not installed on the laptop, so Claude downloaded the official version for the session only.
  • The traps did not appear on their own. Claude had to adjust the sample bus schedules so the closest home really was slow and the far home really was fastest, and added tests so they stay that way.
  • The Google Routes API has no trip start time, which the prompt assumed. The parser works it out from the route duration instead.

Working with the AI

  • Most helpful: building a full app with a server, tests, and offline mode from one detailed prompt, and checking the API documentation before writing code.
  • Where it needed checking: screenshots caught problems that 35 passing tests missed: wrong photos, a confusing comparison, and phone layout bugs.
  • The rate limit worked: the screenshot script itself was blocked after 300 requests a minute, which proved the limit is real.
  • Not yet verified: the real Google transit path, because no API key was available.

Next time

  • Write expected numbers for each trap in the prompt, not only descriptions.
  • Sketch the phone layout too, not only desktop.
  • Get an API key early so real data can be tested.
